# 01. HTTP 와 웹서버 — 통신의 문법

## 한 줄 요약

> 브라우저가 **요청(Request)** 을 보내면 서버가 **응답(Response)** 을 돌려줍니다. 이 주고받음의
> 규칙이 **HTTP** 입니다. 메서드(GET/POST), 상태코드(200/404…), 헤더·바디, 그리고 데이터를
> 담는 **JSON** 까지 — 서버를 만들기 전에 꼭 알아야 할 "통신의 문법"을 정리합니다.

## 1. 웹은 요청과 응답의 반복

웹에서 일어나는 모든 일은 결국 이 한 줄입니다.

```
[브라우저]  ── HTTP 요청(Request)  ─▶  [서버]
[브라우저]  ◀─ HTTP 응답(Response) ──  [서버]
```

주소창에 `https://example.com` 을 치는 것도 사실은 **"이 주소로 GET 요청을 보내줘"** 라는
뜻입니다. 서버는 그 요청을 받아 알맞은 데이터(HTML 페이지, 이미지, JSON 등)를 돌려주고,
브라우저는 받은 결과를 화면에 그립니다.

> 💡 "프론트엔드"는 요청을 보내고 결과를 보여주는 쪽(브라우저), "백엔드"는 요청을 받아
> 처리하고 응답하는 쪽(서버)입니다. 이 자료에서는 둘 다 직접 만들어 봅니다.

## 2. 요청은 무엇으로 이루어지나

HTTP 요청 한 건은 크게 네 부분으로 나뉩니다.

```
PUT /api/led HTTP/1.1                ← ① 메서드 + 경로
Host: localhost:8000                 ← ② 헤더 (요청에 대한 부가 정보)
Content-Type: application/json
                                     ← (빈 줄: 헤더 끝)
{"on": true, "by": "철수"}            ← ③ 바디 (실어 보내는 데이터)
```

| 구성 | 의미 | 예시 |
|------|------|------|
| **메서드** | 무엇을 하려는지 | `GET`, `PUT` |
| **경로(URL)** | 어디에 대해 | `/api/led` |
| **헤더** | 부가 정보(형식·인증 등) | `Content-Type: application/json` |
| **바디** | 함께 보내는 데이터 | `{"on": true, "by": "철수"}` |

> 📌 GET 요청은 보통 **바디가 없습니다**(가져오기만 함). 데이터를 실어 보낼 때는
> POST(생성)나 PUT(변경) 을 쓰고, 그때 바디에 내용을 담습니다.

## 3. HTTP 메서드 — "무엇을 할까"

메서드는 그 요청의 **의도**를 나타냅니다. 입문 단계에서는 `GET` 과 `PUT` 정도면 충분합니다.

| 메서드 | 의미 | 우리 예제에서 |
|--------|------|---------------|
| `GET` | 조회(가져오기) | LED 상태 보기 |
| `PUT` | 변경(교체) | LED 켜기/끄기 |
| `POST` | 생성(보내기) | (새 항목을 추가할 때) |
| `DELETE` | 삭제 | (이 자료 범위 밖) |

> 💡 우리 LED 앱은 **상태 조회(GET)** 와 **상태 변경(PUT)** 만 있으면 되므로 이 둘에 집중합니다.
> `POST`(생성)·`DELETE`(삭제)도 같은 방식으로 씁니다.

## 4. 상태코드 — "어떻게 됐어"

서버는 응답마다 **세 자리 숫자**로 결과를 알려줍니다. 백의 자리만 봐도 분위기를 알 수 있어요.

| 코드 | 뜻 | 언제 |
|------|----|------|
| `200` | 성공 (OK) | 요청이 정상 처리됨 |
| `201` | 생성됨 (Created) | POST로 새 자원이 만들어짐 |
| `400` | 잘못된 요청 (Bad Request) | 보낸 데이터 형식이 틀림 |
| `404` | 없음 (Not Found) | 그런 주소(경로)가 없음 |
| `500` | 서버 오류 (Server Error) | 서버 코드에서 에러 발생 |

```
2xx → 성공      4xx → 내(클라이언트) 잘못      5xx → 서버 잘못
```

> ⚠️ `404` 가 뜨면 대개 **경로 오타**, `500` 이 뜨면 **서버 코드의 버그**, `400` 이면
> **보낸 데이터(JSON) 형식 문제**일 가능성이 큽니다. 코드만 봐도 어디를 봐야 할지 좁혀집니다.

## 5. 데이터는 JSON으로 주고받는다

서버와 브라우저가 **데이터**(HTML 화면이 아니라 값)를 주고받을 때는 거의 항상 **JSON** 을 씁니다.
JSON은 자바스크립트 객체처럼 생긴, 사람이 읽기 쉬운 텍스트 형식입니다.

```json
{
  "on": true,
  "by": "철수",
  "time": "14:03"
}
```

우리 LED 서버의 `GET /api/led` 는 위처럼 **객체 하나**를 돌려줍니다. 여러 개를 담을 땐
대괄호 `[]` 로 묶는 **배열**을 씁니다.

```json
[
  {"on": true,  "by": "철수", "time": "14:03"},
  {"on": false, "by": "영희", "time": "14:05"}
]
```

> 💡 JSON의 규칙은 단순합니다 — **키는 큰따옴표(`"`)**, 값은 문자열/숫자/참거짓/배열/객체.
> 작은따옴표나 마지막 쉼표는 허용되지 않으니 주의하세요.

## 6. REST 감각 — 주소는 "명사", 메서드는 "동사"

요즘 API는 대개 **REST** 스타일을 따릅니다. 어렵게 생각할 것 없이, 이 감각만 챙기세요.

- **주소(경로)** 는 다루는 대상(자원)을 **명사**로 표현 → `/api/led`
- **무엇을 할지**는 **메서드**로 표현 → 상태 보기는 `GET`, 상태 변경은 `PUT`

| 하고 싶은 일 | 요청 |
|--------------|------|
| LED 상태 보기 | `GET /api/led` |
| LED 켜기/끄기 | `PUT /api/led` |

> 📌 그래서 **같은 주소**라도 메서드에 따라 동작이 달라집니다. 우리 서버도 `/api/led`
> 하나에 GET(조회)과 PUT(변경)을 함께 붙입니다.

## 7. 개발자 도구 Network 탭으로 직접 보기

이론은 이쯤! 실제 요청/응답은 브라우저 **개발자 도구**로 눈으로 볼 수 있습니다.

1. 크롬에서 아무 사이트나 열고 **F12** (또는 `Ctrl+Shift+I`)
2. 상단 탭에서 **Network** 선택
3. 페이지를 **새로고침**(F5) → 오고 간 요청 목록이 쭉 나타남
4. 항목 하나를 클릭하면:
   - **Headers** : 메서드, 상태코드, 요청/응답 헤더
   - **Payload** : 내가 보낸 바디(있다면)
   - **Response** : 서버가 돌려준 내용(JSON 등)

> 💡 나중에 우리 LED 앱을 만들 때, Network 탭을 켜 두면 `PUT /api/led` 가
> `200` 으로 잘 갔는지, polling GET이 1초마다 도는지 **눈으로 확인**할 수 있습니다.
> 문제가 생겼을 때 가장 먼저 열어 보는 곳이에요.

## 정리

| 개념 | 핵심 |
|------|------|
| 요청/응답 | 브라우저가 묻고, 서버가 답한다 |
| 메서드 | GET(조회) · PUT(변경) 중심 |
| 상태코드 | 2xx 성공 · 4xx 내 잘못 · 5xx 서버 잘못 |
| 헤더/바디 | 부가 정보 / 실어 보내는 데이터 |
| JSON | 데이터를 담는 텍스트 형식 |
| Network 탭 | 실제 통신을 눈으로 확인 |
