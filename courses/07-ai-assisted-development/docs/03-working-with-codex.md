# 03. Codex 와 일하는 법 — 맥락 · 검토 · git 🧠

## 한 줄 요약

> 좋은 결과의 절반은 **맥락**입니다. 프로젝트 규칙을 **`AGENTS.md`** 에 적어 두면 매번 설명하지 않아도 에이전트가 따릅니다.
> 나머지 절반은 **검토** — 바뀐 내용을 **git diff 로 읽고**, 실행해 확인하고, 작은 단위로 **커밋**합니다.

## 1. AGENTS.md — 프로젝트의 "팀 규칙" 파일

`AGENTS.md` 는 프로젝트 폴더에 두는 **에이전트용 안내문**입니다. Codex 는 작업 시작 전에 이 파일을 읽습니다.
사람 동료에게 주는 온보딩 문서와 같습니다.

```bash
codex
› /init          # 프로젝트를 살펴보고 AGENTS.md 초안을 만들어 줌
```

초안을 열어 우리 규칙에 맞게 고칩니다. 예 — 06 강좌 LED 서버 프로젝트의 `AGENTS.md`:

```markdown
# LED 서버 프로젝트

## 무엇을 만드는가
FastAPI 로 LED 상태 {on, by, time} 을 관리하는 서버. static/ 에 웹 페이지(HTML/CSS/JS).
동아리 교육용이므로 코드는 짧고 주석은 한국어로.

## 기술·규칙
- Python 3.12, FastAPI, uvicorn. 패키지 관리는 **uv** 만 사용 (pip/venv 금지).
  실행: `uv run uvicorn main:app --reload`, 패키지 추가: `uv add <pkg>`
- 프론트는 순수 HTML/CSS/JS (프레임워크·빌드 도구 금지). 포인트 색 #6b4e9e.
- API 경로는 /api/... , 정적 파일 mount 는 main.py 맨 아래 유지.
- 상태 데이터 모양 {on: bool, by: str, time: "HH:MM:SS"} 은 바꾸지 말 것 (ESP32 가 의존).

## 작업 방식
- 변경 전에 무엇을 바꿀지 한 줄로 먼저 말하고, 한 번에 한 기능만.
- 파일을 새로 만들면 README 의 구조 표도 갱신.
- 서버를 띄우는 명령 외의 네트워크 접근은 하지 말 것.
```

**무엇을 적으면 좋은가:**

| 항목 | 예 |
|------|----|
| 프로젝트가 무엇인지 | "FastAPI LED 서버, 교육용" |
| 기술 스택·버전·도구 | "uv 만 사용", "순수 JS" |
| 코딩 규칙 | 주석 언어, 색, 폴더 구조, 바꾸면 안 되는 것 |
| 실행·테스트 방법 | `uv run ...`, `npm run ...` |
| 작업 방식 | "한 번에 한 기능", "먼저 계획 말하기" |

> 💡 요청할 때마다 반복하던 말을 `AGENTS.md` 로 옮기세요. 결과가 일관되고, 팀원 누구나 같은 규칙으로 에이전트를 쓰게 됩니다.
> `AGENTS.md` 는 **git 에 커밋**합니다 — 코드와 함께 진화하는 문서.

## 2. 맥락을 주는 다른 방법

- **파일 지목**: "`static/app.js` 의 `setLed` 함수를 …" 처럼 **파일·함수 이름**을 말하면 정확히 그곳을 봅니다.
- **에러 그대로 붙이기**: 에러 메시지·Traceback 을 **통째로 복사**해 붙이면 원인을 잘 찾습니다. 요약해서 말하지 마세요.
- **이미지**: `codex -i 스크린샷.png` 로 화면 오류나 디자인 시안을 보여 줍니다. (`examples/led-panel/preview.png` 가 그 예)
- **참고 코드**: "06 강좌 `examples/02-led-api/main.py` 와 같은 방식으로" 처럼 기준이 되는 코드를 알려 주기.
- **범위 제한**: "`main.py` 만 고치고 다른 파일은 건드리지 마" — 예상 밖의 수정을 막습니다.

## 3. 작게 쪼개기 — 한 번에 한 기능

```
❌ "LED 서버에 이력 저장, 통계 API, 차트 화면, 다크 모드를 추가해줘"

✅ 1) "이력을 history 리스트에 쌓고 GET /api/history 로 최근 10건을 돌려줘. 다른 건 아직 하지 마"
   → 확인·커밋
   2) "static/index.html 아래에 이력 목록을 표시하고 1초마다 갱신해줘"
   → 확인·커밋
   3) ...
```

작게 시키면 **검토가 쉽고**, 잘못돼도 **되돌리기 쉽고**, 에이전트도 실수를 덜 합니다.

> 💡 큰 작업은 먼저 **"계획만 말해줘, 아직 고치지 마"** 라고 시켜 단계 목록을 받고, 하나씩 진행하세요.

## 4. 검토 — diff 를 읽는 습관

에이전트가 작업을 끝내면 **무엇이 바뀌었는지** 반드시 봅니다.

```bash
› /diff                 # Codex 안에서
git diff                # 터미널에서 (또는 VS Code Source Control 패널 · Git Graph)
git status
```

체크리스트:

- [ ] 요청한 파일**만** 바뀌었나? (엉뚱한 파일이 바뀌었으면 왜인지 물어보기)
- [ ] 요청한 동작이 코드에 들어 있나?
- [ ] 이해 안 되는 부분이 있나? → **"이 부분 한 줄씩 설명해줘"**
- [ ] 없는 함수·라이브러리를 쓰지 않았나? → **실행해서** 확인
- [ ] 비밀정보·큰 파일이 들어가지 않았나?

마음에 안 들면 **되돌리기**:

```bash
git restore .           # 아직 커밋 안 한 변경 전부 취소 (02 강좌)
git restore main.py     # 특정 파일만
```

> 💡 Codex 는 **git 저장소 안**에서 쓸 때 가장 안전합니다. 무엇을 바꿨는지 보이고, 언제든 되돌릴 수 있으니까요.
> 실습 폴더는 시작할 때 `git init` 하고 첫 커밋을 해 두세요.

## 5. git 과 함께 — 작은 커밋

```
요청 → 검토(diff) → 실행 확인 → git add . && git commit -m "이력 API 추가"
요청 → 검토 → 확인 → commit
```

- 기능 하나 = 커밋 하나. 잘못되면 `git revert` / `git reset` 으로 그 단계만 되돌립니다.
- 커밋 메시지도 시킬 수 있습니다: "변경 내용에 맞는 커밋 메시지로 커밋해줘" (git 명령 승인 요청이 뜸 → 읽고 승인)
- **push 는 직접** 하는 것을 권장합니다. 원격에 올라가면 되돌리기가 번거롭습니다.

## 6. 리뷰어로 쓰기 — `/review`, `codex review`

내가(또는 에이전트가) 만든 변경을 **다른 눈**으로 보게 합니다.

```bash
› /review                # 대화 중: 현재 변경 리뷰
codex review             # 터미널: 저장소의 변경 사항 리뷰 (PR 올리기 전에)
codex -s read-only "main.py 를 읽고 버그나 개선점을 알려줘. 수정은 하지 마"
```

> 💡 `read-only` 샌드박스는 "설명·리뷰만" 시킬 때 안전합니다. 실수로 파일이 바뀌는 일이 없습니다.

## 7. 대화 없이 실행 — `codex exec`

한 번 시키고 끝낼 작업, 스크립트에 넣을 작업은 `exec`:

```bash
codex exec "README.md 의 오타를 고치고 결과를 요약해줘"
codex exec -s read-only "이 프로젝트 구조를 3줄로 설명해줘"
```

## 정리

| 하고 싶은 일 | 방법 |
|--------------|------|
| 매번 반복하는 규칙 | **`AGENTS.md`** (`/init` 으로 초안) |
| 정확히 지목 | 파일·함수 이름, 에러 통째로, `-i` 이미지 |
| 안전하게 | 한 번에 한 기능, git 저장소 안에서, 승인 요청 읽기 |
| 검토 | `/diff` · `git diff` · 실행 · "설명해줘" · `git restore` |
| 마무리 | 작은 **커밋**, push 는 직접 |
| 리뷰만 | `/review`, `codex review`, `-s read-only` |
